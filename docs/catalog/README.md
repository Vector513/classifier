## Почему таблицы именно такие

Общее дерево сохранено. GROUP, MODEL и PRODUCT имеют общие код, название, родителя и единицу; для них не нужны три почти одинаковые таблицы. Тип задан явно. GROUP может содержать группы, модели и изделия; MODEL — только PRODUCT-исполнения; PRODUCT не содержит узлов классификации. Физический состав PRODUCT задаётся отдельными строками BOM. Исполнение связано с моделью через parent_id: отдельная дублирующая ссылка model_id не вводилась.

`bom_product` остаётся расширением записи справочника: хранит производственный тип ASSEMBLY/PART/MATERIAL/PURCHASED, а не вторую копию названия и единицы. MODEL и PRODUCT могут участвовать в BOM, GROUP — нет. Единица участника состава зафиксирована после регистрации, чтобы старые нормы не поменяли смысл.

`enumeration_class` сохранён как категория списков (цвет, память, разъёмы). `enumeration` — переиспользуемая характеристика, `enumeration_value` — общий словарь её значений. Это разные абстракции, удаление категории потеряло бы существующую группировку. Старые списки и ID не склеиваются автоматически: у них могут быть разные пользовательские значения и ссылки.

Две новые связи имеют разные задачи. `node_enumeration` отвечает, где характеристика применима. `node_enumeration_option` — какие значения здесь допустимы. Это не новые виды изделий и не копии словаря. У назначения составной ключ (узел, перечисление); у варианта — (узел, перечисление, значение). Дополнительные искусственные ID для этих связей не нужны. При удалении неиспользуемого исполнения его значения и назначения удаляются каскадно; словари и модель сохраняются. Используемые участники BOM защищены ссылками от удаления.

`node_attribute_value` продолжает хранить одно выбранное значение характеристики конкретной записи. Внешний ключ по паре (значение, перечисление) предотвращает несогласованные ссылки. Для модели список доступных цветов хранится отдельно от выбранного значения; старые явно заданные свойства моделей при миграции не теряются.

Числовой параметр, его назначение и фактическое значение также остаются разными понятиями. Назначение наследуется; факты автоматически не копируются потомкам. В частности, цена модели не подменяет цену её исполнения.

Шаблон операции и заполненный документ сохраняются как отдельные абстракции ХО. Склад, остатки и движения запасов в классификатор не добавлялись: справочная модель не описывает наличие физических экземпляров. Текст участника операции сохранён; отдельный справочник контрагентов для задачи классификатора не требуется.

## Пример в интерфейсе

В классификаторе откройте «Электроника → Смартфоны → Apple → iPhone 16». На вкладке «Варианты и свойства» показаны доступные цвета и память. Кнопка «Настроить доступные варианты» меняет набор разрешённых значений, а не выбирает один цвет модели.

Внутри модели есть два исполнения: «iPhone 16 — чёрный, 128 ГБ» и «iPhone 16 — белый, 256 ГБ». В их карточках выбран один цвет и один объём памяти; ОС семейства Apple ограничена iOS. Наследуемая характеристика не теряется после появления исполнений. Имена и цены являются учебными данными.

Пустая группа сохраняет тип «Группа». Браузерная проверка создаёт такую группу на время теста.

При включённых демоданных пустые товарные ветви получают примеры. В ASUS, iPad, Galaxy Tab, аудиотехнике и аксессуарах появляются товары, а у исходных моделей смартфонов и ноутбуков без исполнений — по одному исполнению. Скрипт `catalog-assortment-demo.sql` добавляет записи один раз и учитывает существующие товары, доступные единицы и ограничения характеристик. Учебные цены и разъём USB-C доступны в фильтрах.

У добавленных товаров есть учебная цена, масса и перечислимая характеристика. Дополнительные параметры зависят от товара. У блока питания это мощность в ваттах, у SSD — ёмкость в ГБ, у Galaxy S24 — объём ОЗУ и выбранный вариант памяти. Единицы учёта видны в карточке товара. Кабель видеонаблюдения учитывается в метрах, а демонстрационный USB-C-кабель — в упаковках. Скрипт `catalog-product-details-demo.sql` добавляет значения один раз и сохраняет уже заполненные свойства.

Вкладка «Анализ» позволяет искать по выбранному значению исполнения. Флажок «Также модели, выпускаемые в этом варианте» добавляет модели с допустимым значением.

В «Составах изделий» доступны пять семейств комплектов электроники. Комплект со смартфоном использует существующий Galaxy из классификатора. ХО содержит шаблон закупки электроники, обязательные число, текст и дату, необязательный цвет маркировки упаковки и назначенного поставщика. ХО доступна через SQL. [Составы комплектов и примеры расчёта](../bom/README.md).

## Перенос прежних данных

1. Перед обновлением сохраняется резервная копия PostgreSQL. Для этой работы: `backups/before-catalog-v2-20261108.dump` (каталог исключён из Git).
2. Hibernate добавляет поле типа; `CatalogInitializer` выполняет транзакционный `catalog-schema.sql`. ID узлов, характеристик, выбранных значений и версий BOM сохраняются.
3. Типы старых записей определяются однократно: известные разделы и узлы с детьми — группы, известные модели электроники — модели, остальные старые конечные записи — изделия. У произвольной старой пустой записи невозможно автоматически узнать, задумывалась ли она группой: её тип можно явно исправить в карточке. Участие в BOM сохраняется.
4. Привязки из enumeration.classifier_node_id копируются в node_enumeration; старый столбец удаляется. Единица из старого bom_product.unit_id переносится в справочник, затем столбец удаляется. Стандартные дубли BOM-PCS/BOM-KG объединяются с PCS/KG без изменения количества; исходные записи сохраняются в истории миграции.
5. Исходные узлы, определения параметров, числовые значения, привязки перечислений и старые регистрации BOM записываются JSON-снимком в `schema_migration.details` для `catalog-v2`. Это дополнение к полной резервной копии, а не замена pg_dump.
6. Прежняя bom_seed_history переименовывается в schema_migration; старые отметки загрузки сохраняются. Повторный запуск не восстанавливает удалённый учебный черновик или исполнение и не сбрасывает настройки доступных вариантов.
7. Для прежних значений без назначения восстанавливается назначение. Допустимые варианты учебной модели включают ранее сохранённые её свойства. Новые учебные исполнения создаются только если совместимы с существующими ограничениями.
8. Старый ENUM-параметр ХО с единственным списком категории переносится автоматически. Если в категории несколько списков, миграция требует явно выбрать enumeration_id вместо произвольного угадывания.

Восстанавливать резервную копию следует утилитой версии контейнера, например `docker compose exec -T postgres pg_restore -U classifier -d отдельная_база < backups/before-catalog-v2-20261108.dump`. Проверка восстановления проводится в отдельной БД.
