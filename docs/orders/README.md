# ЛР7: заказы на изделия с вариантами исполнения

Подсистема задачи 2-3-2 реализована в существующем приложении ЛР6. Открыть: [Заказы и конфигурация](http://localhost:8080/#/orders). Сборка и запуск из корня репозитория: `docker compose up -d --build`. Прежние разделы классификатора, составов и маршрутов продолжают работать. Инициализация добавляет таблицы и функции; демонстрационные записи загружаются один раз и не заменяют пользовательские записи.

## Примеры нашего магазина

Добавлен набор электроники: **6 шаблонов, 18 исполнений и 8 заказов**. Есть системные блоки, мобильные рабочие места, смартфоны с аксессуарами, игровая периферия, умный дом и видеонаблюдение. [Состав набора и сценарии проверки](SHOP_EXAMPLES.md).

## Соответствие требованиям

| Требование | Реализация и проверка |
| --- | --- |
| Настроить справочник для вариантов | «Конструктор изделий» → новый шаблон, связанный с MODEL или PRODUCT классификатора. Одна запись — один профиль шаблона. |
| Описать параметры | Код, название, NUMBER/INTEGER/STRING/BOOLEAN/ENUM, обязательность, единица измерения, минимум/максимум, ссылка на общее перечисление. |
| Задать сложные ограничения во время работы | Редактор дерева правил и библиотека функций. Логика, сравнения, арифметика, константы, параметры изделия, формальные аргументы и вложенные вызовы. Перекомпиляция и ввод SQL не нужны. |
| Создать допустимое исполнение | Проверка заполнения, типов, диапазонов, перечислений и всех правил до сохранения. Вариант и значения сохраняются в одной транзакции. |
| Редактировать состав заказа | Заказчик, реквизиты заказа, добавление готового изделия или нового исполнения, замена и удаление позиций, целое положительное количество. |
| Вывести состав с параметрами | Страница заказа и отдельная печатная форма с параметрами, единицами, выбранными значениями перечислений и количеством. |
| Метаданные и SQL-процедуры | `orders-schema.sql`, `orders-logic.sql`; комментарии к таблицам, ограничениям и основным функциям. |
| Проверка процедур | Интеграционные тесты на PostgreSQL 15, повторяемый `demo-check.sql`, браузерный `ui-smoke.cjs`, скриншоты в `screenshots/`. |

В методичке Firebird указан среди рекомендуемых инструментов. Здесь используется PostgreSQL 15 существующего проекта; процедуры адаптированы к PL/pgSQL и сохранённой пользователем физической ER-модели.

## Соответствие диаграммам

Авторитетные модели сохранены без изменения в `models/`: `classes.svg`, `er.png`, `use-cases.png`. Разбор недостающих ограничений: [MODEL_ISSUES.md](MODEL_ISSUES.md).

| Класс | Таблица | Атрибуты и операции |
| --- | --- | --- |
| Заказчик | `customer` | Наименование, контакт, телефон, почта; создание и редактирование реквизитов. |
| Заказ | `customer_order` | Номер, заказчик, дата, срок; создать, изменить, добавить/удалить позицию, получить состав, напечатать. |
| Позиция заказа | `order_line` | Номер, количество, примечание, изделие **либо** вариант; изменить количество, заменить состав позиции. |
| Шаблон изделия | `product_template` | Код, название, ссылка на классификатор; определить параметры, задать правило, создать вариант. |
| Параметр конфигурации | `configuration_parameter` | Код, название, тип, единица, перечисление, обязательность и границы; проверить значение. |
| Вариант исполнения | `product_variant` | Код, название, шаблон; задать значения и проверить весь набор. Неиспользованное исполнение можно редактировать; заказанное заменяется новым. |
| Значение параметра | `variant_parameter_value` | Ссылка на вариант и параметр; JSONB-скаляр либо значение перечисления; установить и получить значение. |
| Правило конфигурации | `configuration_rule` | Код, имя, сообщение, шаблон и корневое выражение; проверить вариант. |
| Выражение | `expression` | Вид, оператор, параметр, формальный аргумент, функция, константа, родитель и порядок; вычислить в контексте фактических значений. |
| Функция ограничения | `constraint_function` | Код, название, тип результата, корень тела; задать сигнатуру/тело и вычислить по фактическим аргументам. |
| Формальный параметр | `formal_parameter` | Функция, номер аргумента, код и тип; проверить тип и подставить фактическое значение. |
| Узел классификатора | `classifier_node` (существует) | Используется как исходное изделие шаблона или готовое изделие в позиции. |

Единицы, перечисления и их значения переиспользуются из прежней БД. Отдельные новые таблицы для них не создаются. Вариант имеет самостоятельный ID и JSONB-факты именно как на сохранённой ER. ENUM хранится ссылкой, без дублирования значения в JSONB.

Архитектура следует ЛР6: контроллер → транзакционный сервис → JDBC-репозиторий → SQL-функции. DTO служат границей REST, а сущности диаграммы представлены таблицами и операциями сервиса/SQL. Дополнительный параллельный слой JPA-сущностей для тех же таблиц не вводится.

## Показ на защите

1. Откройте «Конструктор изделий» → «Воздуховод прямой». Видны параметры `h`, `w`, `L` (мм) и `connection`.
2. В «Библиотеке функций» откройте «Допустимое соотношение сторон»: `AND(a/b >= lower, a/b <= upper)`. Проверьте аргументы `500, 300, 0.5, 2` — результат «Да»; `1000, 100, 0.5, 2` — «Нет».
3. В шаблоне три правила: `0.5 <= h/w <= 2`, `500 < L < 2500`, `connection = FLANGE → L > 1000`. Тело первого использует библиотечную функцию с формальными аргументами.
4. Откройте заказ `ЛР7-0001`: исполнение 500×300×1200 на фланцах, 10 шт., и готовая заглушка, 2 шт.
5. Добавьте исполнение: `h=500`, `w=300`, `L=800`, `connection=FLANGE`. «Проверить ограничения» покажет ошибку фланцевого правила; сохранить нельзя. Для `L=1200` проверка успешна и позиция добавляется вместе с исполнением.
6. Измените или удалите позицию. Откройте «Печать заказа» — видны оба вида позиций и все заданные параметры исполнения.
7. Попробуйте изменить правило так, чтобы оно запрещало уже существующее исполнение: операция отклоняется с сообщением, прежнее правило сохраняется.

Шаблон с ещё не заданными параметрами можно сохранить для последующей настройки; создать пустое исполнение нельзя. Необязательный параметр можно пропустить, но выражение, использующее отсутствующее значение, даёт ошибку проверки. Автоматическое преобразование единиц в формулах не предусмотрено моделью.

## SQL и REST

Основные функции: `get_config_params(template)`, `orders_validation_errors(template, values)`, `check_constraints(template, values)`, `eval_function(function, arguments)`, `create_variant(template, code, name, values)`, `update_variant(variant, code, name, values)`, `create_order(customer, number, date, requested)`, `add_to_order(order, product, variant, quantity, note, line)`, `get_order_contents(order)`.

Значения передаются объектом JSON, например `{"h":500,"w":300,"L":1200,"connection":"FLANGE"}`. Аргументы функций — упорядоченным JSON-массивом. Предикат возвращает BOOLEAN, ошибки проверки — список сообщений. Ошибочная запись откатывается целиком, включая создаваемое дерево выражений и значения исполнения. Проверки SQL действуют и для прямых изменений БД.

REST расположен под `/api/v1/orders`: список заказов и справочников, `/{id}`, `/{id}/document`, `/customers`, `/templates`, `/templates/{id}/parameters`, `/templates/{id}/rules`, `/templates/{id}/validate`, `/templates/{id}/variants`, `/variants/{id}`, `/functions`, `/functions/{id}/evaluate`, `/{id}/lines`, `/{id}/configured-lines`. Документация типов запросов доступна в [Swagger UI](http://localhost:8080/swagger-ui.html).

## Повторение проверок

Java 17 и Docker должны быть доступны. Для Docker Desktop на Linux при необходимости укажите его сокет. Старому Testcontainers в этом проекте с новым Docker нужен API 1.44:

```bash
JAVA_TOOL_OPTIONS=-Dapi.version=1.44 \
DOCKER_HOST=unix://$HOME/.docker/desktop/docker.sock \
bash ./gradlew test bootJar --no-daemon
```

Только новые интеграционные сценарии: `bash ./gradlew test --tests '*OrderControllerTest'`. `OrderControllerTest` проверяет физическую схему, типы и ENUM, арифметику, вложенные функции, порядок аргументов, импликацию, короткое вычисление логики, деление на ноль, атомарность, редактирование, XOR, владельцев записей, защиту исполнений, неверные сигнатуры, циклы и повторную загрузку демоданных. Остальные тесты проверяют сохранение поведения прежних лабораторных. В двух старых фикстурах удаляется созданный инициализатором ЛР6 параметр закупочной цены перед удалением единиц измерения.

Проверка непосредственно в SQL, без сохранения изменений:

```bash
docker exec -i classifier-db psql -U classifier -d classifier -v ON_ERROR_STOP=1 < docs/orders/demo-check.sql
```

Браузерный сценарий создаёт и затем удаляет собственные записи. Запускайте его на **отдельном тестовом экземпляре с демонстрационными данными**, указав установленный модуль Playwright:

```bash
ORDER_TEST_URL=http://127.0.0.1:8082 node docs/orders/ui-smoke.cjs
```

Можно передать `PLAYWRIGHT_MODULE` (путь к модулю) и `PLAYWRIGHT_BROWSERS_PATH`. Сценарий проверяет конструктор правила/функции, защиту существующего исполнения, ввод заказчика/заказа, готового изделия, неверную и верную конфигурацию, печатную форму, мобильную ширину и ошибки JavaScript. Скриншоты сохраняются в `screenshots/`.
