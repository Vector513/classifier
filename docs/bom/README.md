# Спецификации изделий — задание 2.1

Модуль дополняет существующий проект PR1: классификатор, единицы измерения, числовые параметры, перечисления и SQL-таблицы хозяйственных операций сохраняются. Реализованы требования из `Методы/ПримерЗад2_1.docx`, разделы 1.1–1.2, в части приложения, моделей и проверочных сценариев. Полная пояснительная записка на 20 страниц оформляется отдельно; этот файл — техническое описание реализации.

## Контекст и принятые решения

Изучены требования предыдущих ПР, материалы папки «Контекст», имеющийся отчёт и его генераторы в корне, README/PLAN, диаграммы, схема БД, сервисы, контроллеры и интерфейс PR1. Общий справочник хранит группы, модели и изделия в одном дереве с явным node_kind. В BOM регистрируется ссылка на модель или изделие, а не дубликат его кода и названия. Поэтому старые параметры и поиск доступны для того же изделия.

Дерево классификации и граф состава решают разные задачи. Родитель изделия в классификаторе — класс; входящий компонент задаётся строкой спецификации. Один ресурс может встречаться в нескольких позициях и нескольких сборках. Компонент может принадлежать любому классу. Типы по отношению к производству: сборочная единица, деталь, материал, покупное изделие. Тип не запрещает собственную спецификацию: например, деталь может расходовать материал.

Сохраняются PostgreSQL 15, Spring Boot, Kotlin для DTO/сервисов, Java для REST-контроллера и существующий интерфейс на ES-модулях. Firebird в методичке указан как рекомендуемый инструмент; переписывание действующей системы для него не требуется. Новый репозиторий использует JDBC, чтобы SQL-функции расчёта были едиными для приложения и SQL-клиента.

## Версии и наследование

Черновик можно редактировать или удалить. При утверждении состав фиксируется. Изменение оформляется новым черновиком с `baseId`, указывающим на утверждённую версию. То же изделие означает новую редакцию; другое изделие — модификацию. Номер редакции назначается автоматически в пределах изделия. Описание изменения обязательно.

Базовые строки не копируются. Эффективный состав строится по всей цепочке баз: ближайшее определение номера позиции имеет приоритет. Локальное исключение скрывает позицию, включая унаследованную. Отмена локального изменения удаляет переопределение и восстанавливает базовую строку; если базовой строки не было, позиция исчезает. Номер позиции — идентификатор в составе; перенумерация выполняется исключением старой и созданием новой позиции.

Строка может ссылаться на конкретную утверждённую спецификацию компонента. Она должна принадлежать этому же компоненту. Без ссылки компонент считается ресурсом без дальнейшего раскрытия, даже если у него существуют другие версии. Это позволяет явно выбирать покупное или собственное исполнение и не менять прошлый расчёт при создании новой версии компонента.

Единица нормы фиксируется при регистрации изделия в `classifier_node.unit_of_measure_id`; это единица всех его вхождений. Разные единицы в одной позиции и автоматические пересчёты единиц не поддерживаются. Названия/коды и принадлежность классу читаются из текущего справочника; неизменяемость истории относится к составу и количествам, а не к снимку справочника.

## Расчёт и целостность

Для количества `Q` исходных изделий расход по пути равен `Q × q1 × q2 × … × qN`. Повторные вхождения не удаляются: при двух ветвях к одному ресурсу учитываются обе. Итоги группируются по ID ресурса, а не только по классу или единице. В результаты включаются все компоненты выбранного класса, включая промежуточные сборки, если они входят в этот класс. Само исходное изделие не считается своим компонентом.

Проверяются прямые и косвенные циклы по изделиям, в том числе через старую версию того же изделия. При обнаружении цикла изменение откатывается. SQL-обход дополнительно помечает цикл и прекращает рекурсию по этой ветви; сервис не возвращает частичный расчёт. Нет искусственного ограничения глубины, но большие графы требуют соразмерных ресурсов сервера.

Внешние ключи защищают используемые изделия, единицы и базовые версии от удаления. SQL-триггеры запрещают изменение утверждённых версий и их строк, неутверждённые базы и несовместимые ссылки на версии компонентов. При утверждении проверяются пустой состав и циклы. Все изменения BOM через сервис сериализованы транзакционной advisory-блокировкой: назначение редакций и проверка состава не конфликтуют с параллельными изменениями модуля. Рекомендуемый путь редактирования — REST API; прямые SQL-скрипты должны выполнять согласованный набор изменений в одной транзакции.

`BomInitializer` загружает дополнение после JPA и прежних SQL-скриптов. Таблицы создаются при отсутствии, функции и триггеры обновляются без удаления данных. Это аддитивное расширение; для будущих несовместимых изменений потребуется полноценная миграция схемы.

## Интерфейс и API

Раздел **Составы изделий**: `http://localhost:8082/#/bom`. Создайте изделие в классификаторе и зарегистрируйте его в разделе спецификаций. Затем создайте черновик, добавьте позиции, проверьте раскрытие/расход и утвердите версию. Для изменения нажмите «Создать новую версию / модификацию» и выберите изделие и базу.

Базовый путь API: `/api/v1/bom`.

| Метод и путь | Назначение |
|---|---|
| `GET /products`, `POST /products` | Изделия; регистрация `{nodeId, kind, unitId}` |
| `GET /specifications`, `GET /specifications/{id}` | История версий и карточка |
| `POST /specifications` | Черновик `{productId, baseId?, description}` |
| `DELETE /specifications/{id}` | Удаление черновика |
| `POST /specifications/{id}/release` | Утверждение |
| `GET /specifications/{id}/lines` | Эффективный состав с указанием источника |
| `PUT /specifications/{id}/lines/{position}` | Добавление/замена `{componentId, componentSpecificationId?, quantity}` |
| `DELETE /specifications/{id}/lines/{position}` | Исключение позиции |
| `GET /specifications/{id}/local-positions` | Номера локальных изменений, включая исключения |
| `DELETE /specifications/{id}/overrides/{position}` | Отмена локального изменения |
| `GET /specifications/{id}/explosion?quantity=3` | Полное раскрытие |
| `GET /specifications/{id}/totals?quantity=3&classId=…` | Итоги по классу ресурсов |

Ошибки: 404 — отсутствующая ссылка; 400 — цикл; 409 — редактирование утверждённой версии или конфликт ограничений БД; 422 — неверная норма, номер позиции, пустой состав, неутверждённая/чужая версия компонента. Норма допускает 13 целых и 6 дробных знаков; количество исходных изделий положительное с теми же пределами. Промежуточные SQL-вычисления используют `numeric` без округления до масштаба строки.

## Как попробовать модуль на демонстрационных данных

`demo.sql` также добавляет краску и учебный черновик второй версии корпуса. Уже существующие версии и пользовательские изменения при повторной загрузке сохраняются.

1. Откройте раздел «Составы изделий» и выберите `BOM-HOUSING`, версия 1. В составе два кронштейна, 0.25 кг стали и один болт. Ссылка на версию кронштейна открывает его собственный состав: 0.5 кг стали и три болта.
2. В расчёте укажите количество `3` и класс `BOM-MATERIALS — Материалы`: результат — 3.75 кг стали. Выберите `BOM-DEMO`, чтобы увидеть также суммарное количество кронштейнов и болтов.
3. Откройте `BOM-HOUSING-M`, версия 1: кронштейн унаследован, прямая норма стали заменена на 1 кг, отдельный болт исключён. На три изделия нужно 6 кг стали.
4. Откройте `BOM-HOUSING`, версия 2, со статусом «Черновик». Здесь сталь заменена на 0.75 кг, отдельный болт исключён, добавлено 0.1 кг краски. На три изделия результат — 5.25 кг стали и 0.3 кг краски.
5. Нажмите «Изменить» у стали и задайте норму `1`. Повторите расчёт: расход стали станет 6 кг. Чтобы вернуть базовые 0.25 кг в этой позиции, нажмите «Вернуть как было» у строки 2 в блоке «Изменения этой версии».
6. «Вернуть как было» у строки 3 восстановит исключённый отдельный болт. «Отменить добавление» у строки 4 уберёт добавленную краску, поскольку этой позиции нет в базе.
7. «Добавить компонент» позволяет выбрать любой зарегистрированный компонент. Норма задаётся на одно изделие. Версию компонента выбирайте, если нужно раскрыть его внутренний состав.
8. После экспериментов можно утвердить черновик: редактирование этой версии закроется. Для дальнейших изменений используйте «Создать новую версию / модификацию». Первая утверждённая версия корпуса остаётся прежней.

Для обыччного запуска адрес берётся из конфигурации: `8082` при `bootRun`, `8080` при Docker Compose.


## Первый запуск на другом устройстве

Из каталога `PR1` выполните `docker compose up -d --build` и откройте `http://localhost:8080/#/bom`. Новая БД получит прежний справочник электроники и демонстрационный набор: кронштейн, корпус, усиленный корпус, сталь, болты, краску и учебную вторую редакцию корпуса. Числовые ID могут отличаться — выбирайте примеры по коду и номеру версии.

В Compose установлено `CLASSIFIER_DEMO_ENABLED: "true"`. Инициализатор сначала создаёт схему BOM, затем выполняет `src/main/resources/bom-demo.sql`. Скрипт и отметка `schema_migration` выполняются атомарно под блокировкой. После успешной загрузки повторные запуски не меняют примеры, включая отредактированные и удалённые позиции/черновики. Для `bootRun` автозагрузка по умолчанию выключена; при необходимости задайте ту же переменную окружения. Автоматически переносится подготовленный демонстрационный набор, а не произвольные пользовательские записи из БД разработчика.

## Обновление интерфейса и проверка 04.11.2026

Раздел переименован в «Составы изделий»; термин «спецификация» объяснён во вводном тексте. На главной странице добавлен переход к составам. Инструкция в три шага, словарь, поиск по названию/коду и фильтр статусов помогают начать работу без знания терминов. В узком окне строки таблиц превращаются в карточки с подписями, чтобы кнопки действий оставались доступны без горизонтальной прокрутки.

Карточка показывает название изделия, состояние версии и прямой состав. Блок изменений сравнивает исходные и текущие строки, включая исключённые. Кнопки объясняют последствия: «Вернуть как было» восстанавливает базовую строку, «Отменить добавление» удаляет новую. Удаление собственной строки без базы требует подтверждения, поскольку восстановить её из базы невозможно.

В форме строки показываются единица измерения и только утверждённые версии выбранного компонента. Смена компонента сбрасывает несовместимую ссылку. Добавление в занятый номер строки блокируется, чтобы случайно не заменить другой компонент. Расчёт принимает десятичную запятую, по умолчанию показывает все компоненты и позволяет выбрать группу со всеми подгруппами. Изменение условий помечает результат как устаревший; ответ старого запроса не заменяет более новый.

Тип исходного учебного кронштейна исправлен с PART на ASSEMBLY. Для существующих демонстрационных данных `bom-demo-updates.sql` распознаёт прежний пример по коду, названию, группе и исходному составу. Исправление отмечается в `schema_migration` и не повторяется. Пользовательские рецептуры и версии не изменяются.

Проверки текущего обновления:

Сверка с разделом 1.2 методички: модели вариантов использования, классов и хранения находятся в `*.puml`; SQL-схема и функции — в `src/main/resources/bom.sql`; исходные данные, описания проверок, тестовые сценарии и скриншоты приложены здесь. Диаграмма вариантов использования описывает действия конструктора (ведение состава и утверждение) и технолога (раскрытие и расчёт). Диаграмма классов разделяет данные, контроллер, сервис с проверками и репозиторий SQL. ER-модель фиксирует ссылки на изделие, базовую версию и версию компонента. Полная пояснительная записка объёмом не менее 20 страниц из методички в это обновление интерфейса не входит и ещё требует отдельного оформления.

С 08.11.2026 модели и изделия определяются явным типом, единица нормы берётся из classifier_node; прежняя bom_seed_history перенесена в schema_migration. Актуальная общая модель и результаты проверки описаны в [анализе классификатора](../catalog/README.md).
